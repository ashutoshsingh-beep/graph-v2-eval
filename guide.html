1. Goal

Covlant turns a repository into a code graph: the functions and files in the code, and which function calls which. Everything else Covlant does is built on this graph. A new engine, graph v2, will replace the current one.

Numbers alone do not tell us what to fix. Your job is to:

  1. Verify the differences between the two graphs by reading the code. A machine sorts every call into groups ("only dev gets it right", "only v2 gets it right", and so on). You check samples of each group and say whether the machine is right.
  2. Find the gaps: the calls v2 misses that the old engine gets right. Group them by cause, so each cause becomes one fix for the graph v2 team.
  3. Record speed and memory for both engines on the same repository.
  4. Question the comparison itself: say where the machine or the oracle is wrong, or what it cannot see (sections 8 and 15).
  5. Send one report per repository every day (section 13).

codeparser branchdevelopmentfleet/graph-v2 (default). It holds everything in feat/graph-v2 plus newer work (1,474 commits ahead on 23 November 2026).

To test feat/graph-v2 instead, put V2_REF=origin/feat/graph-v2 in front of each command.

2. Words you need

WordMeaning
OracleThe answer key: a SCIP indexer (scip-python, scip-go, scip-typescript) that uses the language's type checker to find every call and its target. It is independent of both engines, and it is not always right. That is why a person verifies.
Call (obligation)One call the oracle found, to a function in the same repository: a file, a line, and the function(s) it reaches.
EdgeOne "this line calls that function" claim in an engine's graph.
RecallOf the calls the oracle found, the share for which the engine has a right edge.
PrecisionOf the edges an engine made (on lines the oracle can judge), the share that are right.
n, intervaln is how many items a figure is based on. The 95% interval is the range in brackets.
Tier (v2)How v2 resolved an edge: exact, import, name, external, or unresolved.
Reported miss (v2)v2 did not resolve the call, but left an unresolved edge at that call with a reason: dynamic_dispatch, no_candidate, many_candidates, reflection, external_not_indexed, depth_cap. v2 knows it missed this call.
Silent miss (v2)v2 has no edge at all at that call, so the graph gives no sign of the miss. (v2's ledger file may still hold a note; the kit does not read it yet.) Silent misses are worse than reported ones.
Accounting (v2)v2's self-check: everything it read is placed in the graph or written to its ledger. lost must be 0.

1. setup→2. run→3. scores→4. verify rows→5. group gaps by cause→6. report→7. issues 
cd ~/graph-v2-qa
kit/graph-eval.sh run repos.tsv            # or: run repos.tsv <tag>; default tag is the date and time

#   ... verify rows in eval/<tag>/out/<repo>-differences.md ...

For each repository, run:

  1. pins the repository commit and the two engine commits in eval/<tag>/manifest.toml;
  2. checks out the repository, and checks that nothing in it changes during the run;
  3. builds the oracle index (cached after the first time);
  4. builds the graph twice with each engine and measures wall time and peak memory;
  5. scores both graphs (codeparser's scripts/accuracy/scip_eval.py; method in docs/graph-v2/accuracy-method.md);
  6. compares the two graphs call by call, checks its counts against the scores, and writes the differences sheet. Verdicts from your newest earlier sheet are copied in (section 7.6).

click and cobra take about 30 seconds each. Keep the laptop idle during a run, or the time and memory numbers are wrong. Repositories run one at a time; if one fails, the others still run. At the end, FAILED: <name> means no result, and CHECK FAILED: <name> means the scorer found a problem such as output that differs between the two builds. That is an S1 finding. In both cases the command exits with code 1.

7. How the comparison works

Read this before you verify. If you find a case where these rules give the wrong answer, that is a finding (section 15).

7.1 What counts as one call

  1. The oracle lists every place where a name is used and a ( follows it (the scorer's is_call_site). Each place has a byte position and the function(s) the name refers to.
  2. The kit keeps only calls to functions inside the repository. Calls into libraries are scored separately as "external", and only for v2, because dev makes no external edges.
  3. The old engine records only a line number for each call, not a byte position. So both engines are compared per line: one obligation is (file, line, the oracle's target set). Two identical calls on one line count as one.

7.2 When an edge is "right"

An engine's edge on a line is right for an obligation on that line when its target is the engine's node for the oracle's target. The mapping from the oracle's target to an engine node is:

  • v2: the smallest v2 node with that name whose span holds the definition. A call to a class also accepts the class's constructor.
  • dev: the dev node with that name in the same file and the same enclosing scope, at or before the definition line. A class also accepts its constructor.
  • If the engine has no node for the target, no edge can be right. The call stays in the count as a miss (an engine must not shrink its own denominator).

7.3 The groups (recall side: one row per call)

GroupRuleCounts towards
both_rightBoth engines have a right edge on the line.Both recalls
gapdev has a right edge on the line; v2 has none.dev recall only
v2_gainv2 has a right edge; dev has none.v2 recall only
both_missNeither has a right edge.Neither

So v2 recall = (both right + v2 gain) ÷ calls, and dev recall = (both right + gap) ÷ calls. The kit checks this against the published scores on every run and prints check OK or MISMATCH.

7.4 How v2 missed (the "notes" column)

For a gap or both-miss call, the kit looks at v2's edges at the exact byte position of the call, not the whole line, and gives one type:

v2 missRule, in this order
no_nodev2 has no node for the oracle's target.
wrong_targetv2 has a resolved in-repo edge at this call, to another function.
externalv2 has an external edge at this call: it thinks the function is in a library.
reported (reason)v2 has only unresolved edges at this call. The reason is v2's.
silentv2 has no edge at this call at all.

The notes column also carries flags:

  • oracle reads a definition as a call: the line defines a function with the same name as the oracle's target, for example a second def getchar for another platform, or the real def main( after its @overload stubs. The oracle took the definition for a call to the earlier one. Expect the verdict oracle wrong.
  • dev has N targets on this line: dev was right, but it emitted several functions on the line and one of them matched. dev may have guessed by name. Judge whether dev really knew.
  • dev has no node for the target: dev could not be right.

7.5 Wrong edges (precision side: one row per edge)

GroupRule
v2_wrongA v2 in-repo edge on a line where the oracle has at least one call it can map, whose target is none of that line's targets. at call site: no means the edge sits on no call the oracle saw, for example a decorator line.
dev_wrongThe same, for dev.
v2_unscored, dev_unscoredEdges on lines where the oracle has no call it can map. No score uses them. They can be calls the oracle missed, or plain wrong edges. A small sample is in the sheet.

Line precision = right ÷ (right + wrong). Each engine is judged on its own edges, so the two engines are judged on different lines. Also look at v2's precision at exact call sites, which the scorer computes from byte positions (dev has no byte positions).

7.6 Samples, and keeping your work

  • Each group gets up to 25 rows (wrong dev edges 15; unscored and both-right 10). The draw is seeded, so the same input gives the same rows.
  • The draw is stratified: one row per kind in turn (by miss type and reason, or at-site yes/no), so one big pattern cannot fill the whole sheet. So the sample share of a kind is not its share of the repository. Use the counts table and rows.tsv for sizes.
  • Each run copies your verdicts, causes and Status block from your newest earlier sheet of that repository, for every row whose file, line, oracle, dev and v2 text are unchanged. Rows you already judged are drawn first. When an engine changes a row, the row comes back empty: judge it again.
  • 25 rows tell you a rate to about ±20 percentage points. Do not read small differences in the sample.

7.7 A small example

src/click/core.py:1552    commands = self.list_commands(ctx)
  oracle:  src/click/core.py:1764 MultiCommand#list_commands().
  dev:     method::src/click/core.py::CommandCollection::list_commands; ...::Group::list_commands; ...::MultiCommand::list_commands
  v2:      unresolved (dynamic_dispatch) at this call
  group:   gap    (dev has a right edge on the line, v2 has none)
  notes:   reported (dynamic_dispatch); dev has 3 targets on this line

Here dev "wins" because it emitted every list_commands it knew, and one was right; its other two edges appear as wrong dev edges. v2 gave up and said why. Your verdict says whether that is really a v2 gap, and the cause names the code shape (method on self, defined in the class).

Do these checks on every new repository, and write what you find in the report's Status block or as an S4 issue.

10. Verify the differences

10.1 Each row

ColumnMeaning
file:line, sourceThe call or the edge. Open it in ~/graph-v2-qa/work/<repo>/src.
oracleWhere the oracle says the call goes: file:line Symbol.
devdev's edges on that line (node ids such as method::src/click/core.py::Command::invoke), or no edge.
v2v2's edges at the call (or on the line), with their tier.
notesThe v2 miss type and the flags (7.4).
verdict, cause, reason trueYou fill them in.

10.2 How to verify one row

  1. Open the line. Find what the call is on: a module function, self.x(), super().x(), a method on a parameter or field, a decorator, an element of a list.
  2. Find where it really goes: follow the import, the class of the object, its base classes, or the type annotation. "Go to definition" in your editor is only a hint; it is the same kind of tool as the oracle.
  3. Fill in verdict:
    VerdictUse when
    confirmedThe row is what its group says. Gap: the oracle and dev are right, v2 is wrong. v2 gain: the oracle and v2 are right, dev is wrong. Both miss: the oracle is right and both engines are wrong. Wrong edge: the edge really goes nowhere the code goes. Both right: both are right.
    oracle wrongThe oracle's target is wrong, so the row is not a real difference.
    dev wrongdev's edge points somewhere else after all.
    v2 right after allv2's edge is right or acceptable (for example, a call that can reach either target at run time).
    ?You cannot decide in 10 minutes. Ask the lead at the end of the day.
  4. For a confirmed gap, both miss or wrong v2 edge, fill in cause: a short phrase that fits every call with the same problem. For example: self method inherited from base class, method on element of named slice type, decorator application edge. Reuse the same phrase for the same cause; the report groups by it.
  5. For a reported v2 miss, fill in reason true: yes if the reason fits (for example dynamic_dispatch on a method of a parameter with no type), no if it does not (for example dynamic_dispatch on self.method() whose class is plain to see).

Order of work: gaps, then wrong v2 edges, then both right (the spot check), then v2 gains, then the rest.

11. Find the gap patterns

A gap pattern is one cause of v2 misses that the graph v2 team can fix once. To find them:

  1. Sort your confirmed gap and wrong-edge rows by the cause column. The daily report does this for you.
  2. Size each cause in the whole repository with rows.tsv, not the sample: 
    awk -F'\t' '$1=="gap" && $4 ~ /dynamic_dispatch/' eval/<tag>/out/<repo>-rows.tsv | wc -l     # gaps v2 reports as dynamic_dispatch
awk -F'\t' '$1=="gap" && $8 ~ /self\.fail\(/'   eval/<tag>/out/<repo>-rows.tsv | wc -l     # gaps on one code shape
  3. Mark each pattern reported or silent. Silent patterns come first: v2 does not know about them, so nothing downstream can warn about them either.
  4. Check that the pattern is general, not one odd line. You need at least 3 rows, ideally in different files.
  5. Check the same pattern in a second repository of the same language if you have one.

11.1 Severity

LevelRule
S1Not deterministic; accounting lost above 0; the build fails; files fail to parse; the counts check says MISMATCH.
S2A confirmed gap pattern covering 20 or more calls, or a silent one with 3 or more confirmed rows. A wrong-edge pattern covering 20 or more edges.
S3A smaller gap or wrong-edge pattern. A false v2 reason. A both-miss pattern.
S4A report, tool or scorer problem, or an oracle problem (many oracle wrong).

16. Common mistakes

  • Different engines. Use the lead's commit pair. Re-check a pattern on today's commits before you file it.
  • One issue per row. Group rows by cause. 134 rows with one cause are one issue.
  • Trusting the oracle. It is a strong tool, not the truth. The code is the truth.
  • Ranking on line precision. Read it with the call-site figure and the wrong-edge rows.
  • Sizing a pattern from the sample. The sample is stratified. Use rows.tsv.
  • A cause that names a line. "core.py:1552 broken" is not a cause. "method on self defined in a base class" is.
  • Small n. Look at n before the percentage.
  • Busy laptop. Other work during a run spoils the time and memory numbers.
  • A failed repository. It still gets a report marked FAILED, with the reason. Send it, so the lead sees it.
  • Editing the sheet's machine columns. Only fill in verdict, cause, reason true and the Status block; the next run matches rows on the other columns.
  • Coverage. Out of scope here.
